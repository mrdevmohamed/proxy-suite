# 06 — مواصفة VLESS (كما هي منفذة)

بروتوكول VLESS خفيف وعديم الحالة: يرسل العميل الهوية والوجهة في هيدر واحد،
فيتحقق الخادم ويتصل. ولا مصافحة beyond ذلك.

> النطاق: يوثق هذا **المجموعة الفرعية المنفذة في `servers/vless-ws-V2.ts`**
> (‏VLESS فوق WebSocket للـTCP فقط). والمواصفة الأصلية الكاملة تعرّف أيضًا UDP
> وتدفقات XTLS/Vision — وهي مذكورة هنا لكنها مرفوضة.

## هيدر الطلب (عميل ← خادم، أول إطار WS ثنائي)

```
version      : بايت واحد  (يُعاد صداه في الرد، عادة 0x00)
uuid         : ‏16 بايتًا (UUID بصيغة RFC-4122 الثنائية)
addons_len   : بايت واحد  (‏N — طول `addons` وغالبًا 0x00)
addons       : ‏N بايت    (يُتجاهل ويُتخطى)
command      : بايت واحد  (‏0x01 للـTCP — القيمة الوحيدة المدعومة هنا)
port         : بايتان     (منفذ الوجهة big-endian)
address_type : بايت واحد  (‏0x01 للـIPv4 | ‏0x02 للنطاق | ‏0x03 للـIPv6)
address      : متغير      (انظر أدناه)
payload      : الباقي     (أول بايتات التطبيق، وقد يكون فارغًا)
```

على السلك:

```
ver || uuid16 || addons_len || addons || cmd || port16 || atyp || addr || payload
```

أدنى طول للهيدر: `1+16+1+1+2+1 = 22` بايتًا. والأقصر → `null` (انتظار مزيد من
الإطارات في V2؛ أما V1 فيرمي `VLESS header is incomplete`).

## ترميز العنوان (`atyp`)

| `atyp` | البنية | مثال |
|--------|--------|------|
| `0x01` ‏IPv4 | ‏4 بايتات `a.b.c.d` | `127,0,0,1` |
| `0x02` نطاق | بايت `len` + ‏`len` بايت UTF-8 | `0x0B "example.com"` |
| `0x03` ‏IPv6 | ‏16 بايتًا، 8 مجموعات big-endian | `::1` ← `0:0:0:0:0:0:0:1` |

أي `atyp` آخر → خطأ `0x01 ‏(GENERAL)`. والعنوان المبتور → `0x01`.

## معالجة الأمر

| `cmd` | المعنى | هذا الخادم |
|-------|--------|------------|
| `0x01` | ‏TCP | ✅ اتصال + تمرير |
| `0x02` | ‏UDP | ❌ مرفوض `0x02` ‏UNSUPPORTED_COMMAND (محجوز) |
| غيره | — | ❌ مرفوض `0x02` ‏UNSUPPORTED_COMMAND |

## الرد (خادم ← عميل)

دائمًا بايتان:

```
[ version, code ]
```

| الرمز | الثابت | متى |
|-------|--------|-----|
| `0x00` | `SUCCESS` | نجح الاتصال TCP؛ ويبدأ تمرير الحمولة |
| `0x01` | `GENERAL` | ‏addons/عنوان/منفذ سيئ أو فشل الاتصال/المهلة |
| `0x02` | `UNSUPPORTED_COMMAND` | أمر سيئ/UDP |
| `0x03` | `INVALID_UUID` | عدم تطابق UUID ‏(`timingSafeEqual`) |

يرسل V2 رد الخطأ عندما يُستلم بايت الإصدار على الأقل ثم يغلق.
(أما V1 ‏`sendResponse` فيرسل `[version, 0x00]` عند النجاح فقط ويغلق بصمت عند الخطأ.)

## مثال عملي (IPv4)

الـUUID ‏`00000000-0000-4000-8000-000000000001` ← `00…00 40 00 80 00 00…01` ‏(16 بايتًا).
الوجهة `127.0.0.1:8080` ‏(`8080 = 0x1F90`) والحمولة `"Hi"`:

```
00 | 00000000 00004000 80000000 000001 | 00 | 01 | 1F90 | 01 7F000001 | 4869
ver| uuid16                           | AL | cmd| port | atyp addr    | payload
```

بانٍ الاختبار: `buildVlessHeader("127.0.0.1", 8080, "Hi")` في `tests/helpers.ts`.

## ملاحظات سلوكية (V2)

- **التخزين المؤقت:** تتراكم الإطارات في `headerChunks` حتى ينجح `parseVless` أو
  يخطئ؛ وإذا تجاوز `headerSize ‏4096` ‏(`MAX_HEADER_SIZE`) يُغلق فورًا.
- **فحص UUID:** ‏`crypto.timingSafeEqual` على 16 بايتًا (مع فحص الطول أولًا).
- **الاتصال:** `net.createConnection({host, port})` مع **مهلة 10 ثوانٍ**؛ وعند
  الفشل يُرسل `[version, 0x01]` ويُغلق. ويُمسح مؤقت المهلة عند الاتصال **والخطأ**.
- **التمرير:** تُكتب الحمولة الأولية دفعة واحدة؛ وإطارات العميل اللاحقة ←
  `remote.write`؛ وبيانات `remote` ← `ws.send`. وإغلاق/خطأ `remote` ← تنظيف
  (تدمير + `ws.close`).
- **الإطارات النصية تُتجاهل** (`isBinary === false` ← عودة).
- **حدود WS:** ‏`maxPayload: 16 MB`؛ ويجب أن يطابق مسار الترقية `websocket.path`
  تمامًا وإلا دُمّر المقبس.

## رابط العميل (هذا المشروع)

```
vless://<uuid>@<server.host>:<port>?encryption=none&security=none&type=ws&host=<server.host>&path=<path-مشفّر>#<name-مشفر>
```

الحقل `encryption` دائمًا `none` (فلا تشفير مدمج في VLESS). ومع حافة TLS
يتحول العملاء إلى `security=tls` مع المنفذ 443.
